# 先可比，再判断

组合 `knowledge` 和 `sql` 取得本轮原文与实际执行结果。先逐项核对时间窗口/截止、地区、品类归属、支付队列、事件状态、单位、粒度、去重和业务政策版本。不要把资料入库revision当政策版本。

## 分类规则

| 情况 | 展示方式 |
| --- | --- |
| 文档对业务事实的陈述与SQL在同一口径下不同 | `kind=conflict`，`comparable=true`；并列两份来源与差异，不静默择一，不猜报表错误原因 |
| 制度是规范要求，记录可完整计算并违反适用要求 | `kind=execution_deviation`，`comparable=true`；说明适用版本、规则上限和实际耗时，这是执行偏差，不是文档事实冲突 |
| 缺少计算必需的字段，或两边范围尚未对齐 | `kind=missing_data`，`comparable=false`；标题和结论写“无法判定/不可直接比较”，列缺失项，绝不称已确认超时 |
| 同口径查得高比例但样本很少 | `kind=small_sample`，`comparable=true`；这里true只表示来源与范围可对齐，不能据此外推总体或因果 |
| 核对定义资料后发现指标未定义 | `kind=missing_definition`，`comparable=false`，无需SQL时`result_id=""`；随后`ask_clarification`，不能换成退款率计算 |

`checks` 写已核验的业务事实和可比条件，`limitations` 写仍缺的资料与不能作出的判断。数值只能来自本轮SQL；文档引述只能来自本轮 `evidence_ids`。成功展示只证明来源归属，语义结论仍须自行核对。

零分母但记录字段完整，表示没有合格支付样本，不是缺字段；保留0、0和NULL并说明，不用 `missing_data` 把真实零值当作资料丢失。

只有问题确实要求文档事实/制度与数据对照，或观察到相关冲突与异常，才用核对卡。仅引用定义计算一个普通指标，无需额外生成“核验一致”卡来补齐组件。

如果用户要求单笔核验，且规则和完整记录支持按时/符合要求，用 `kind=consistent`、`comparable=true` 展示一致核验。普通无异常统计无需强行调用核对卡。纯文档冲突直接并列引用，不虚构SQL来满足卡片参数。

已经对齐并证实差异后，原因未知可以直接报告；不要为了推测月报取数方式而新增一串用户未要求的SQL试算。

对政策宽松、质量问题、数据异常等“为什么”问题，即使查到高退款率也只能描述观察结果；没有因果证据就说明无法归因，给出待核验方向。较大范围的退款率低或相似，也不能据此宣布“品类整体健康/没有质量问题”；没有已取得的基准也不能称“正常区间”，业务比例不等于质量鉴定。

用户只问一个分组的极端比例能否外推时，取得该组分子、分母和样本边界已足够；不为证明正常或异常，主动遍历其他地区、品类和全国水平。只有用户要求比较，或核实已发现的事实差异时，才追加对应范围查询。

最后简洁回答用户：能确认什么、不能确认什么、需要补充什么。不要重复整张卡片或把等待澄清的任务标为完成。
